## A) Git ve GitHub Temel Kavramları

Örneklerin hepsini kendi bilgisayarımda denedim. Önce `git-deneme` adında test reposu açtım, içine `notlar.txt` adında bir dosya koydum ve commit, branch, merge, push, pull işlemlerini bu dosya üzerinden yaptım.

İlk olarak adımı ve e-posta adresimi tanıttım. Burada önceden bilgisayarıma Git'i kurduğum için okul mailim üzerinden değil, kişisel mailim üzerinden devam ettim.


### 1) Repository
Repository, projenin bütün dosyalarını ve bu dosyaların geçmişini tutar. İçinde bir .git klasörü tutar.

Repository iki yerde olabilir
 **Local repo:** Kendi bilgisayarımdaki kopya.
 **Remote repo:** GitHub'daki kopya. Takım bu kopya üzerinden çalışır.

### 2) Stage
Dosyayı değiştirirken o değişikliği kaydeden alandır. Her şey otomatik olarak kaydedilmez. Hangi değişikliklerin bir sonraki commit'e gireceğini git add ile seçeriz.


### 3) Commit
Stage'deki değişikliklerin kalıcı bir kaydıdır. Her commit'in benzersiz bir kimliği ve bir mesajı vardır. Gerektiğinde herhangi bir commit'e geri dönülebilir.


### 4) Branch
Projenin ayrı bir çalışma koludur. Ana koda dokunmadan yeni bir özellik denemek veya bir hatayı düzeltmek için branch açılır.


### 5) Merge
Bir branch'taki değişiklikleri başka bir branch'e aktarma işlemidir. Genelde bir özellik kendi branch'ında tamamlayıp test edildikten sonra main'e merge edilir.


### 6) Push
Yerel repodaki commit'leri uzak repoya gönderme işlemidir. Push yapılmayan commit'ler sadece bilgisayarımda kalır ve takım arkadaşları göremez.


### 7) Pull
Push'un tersidir. Uzak repodaki yeni commit'leri yerel repoya indirip birleştirir. Takımda başka biri kod gönderdiyse çalışmaya başlamadan önce git pull yapmak gerekir.


## B) Takımlar Neden Git ve GitHub Kullanır?

### 1) Versiyon kontrolüne neden ihtiyaç duyulur?
 **Versiyon kontrolü olmayan bir projede kod USB bellek, zip dosyası ya da bir Drive klasörü olarak paylaşılabilir.**
 **Hangi dosyanın güncel olduğu bilinmez.**
 **Birbirinin işini ezme.**
 **Neyin, neden değiştiği bilinmez.**
 **Geri dönülemez.**

Her commit kimin, ne zaman, neyi ve hangi mesajla değiştirdiğini kaydeder. git log ile geçmiş, git diff ile iki sürüm arasındaki fark satır satır görülebilir.

Ortak çalışılan branch'lerde git revert tercih edilmelidir. Geçmişi silmediği için diğer takım üyelerinin reposunu bozmaz.

### 2) Git ile GitHub arasındaki fark

| | **Git** | **GitHub** |
|---|---|---|
| Ne? | Versiyon kontrol aracı | Git repolarını barındıran web platformu |
| Nerede çalışır? | Kendi bilgisayarımda, internetsiz de çalışır | İnternette, github.com üzerinde |
| Kim yaptı? | Linus Torvalds | GitHub Inc. |
| Ne sağlar? | commit, branch, merge, geçmiş takibi | Uzak repo, pull request, code review, Issues, Actions, Wiki |


**GitHub'a alternatif platformlar**
**GitLab**, **Bitbucket**, **Azure DevOps**, **Gitea Forgejo**, **Codeberg**

### 3) Ekip çalışmasına katkıları

Her üye kendi işi için ayrı bir branch açabilir.
PR'da hangi dosyaların ve satırların değiştiği görünür, kod birleştirilmeden önce takım tarafından incelenir.
Başka bir takım üyesi PR'daki kodu okuyup yorum yapabilir, hata veya iyileştirme önermesi verebilir. Böylece hatalar main'e girmeden yakalanır.

### 4) GitHub'ın proje yönetimi özellikleri

 **Issues**
 **Projects**
 **README ve Markdown**
 **Wiki**
 **Actions**
 **Releases ve Tags**
 **Branch protection**
 **Discussions**

### 5) Kulüp ve Takımlar
 **Kodu kişisel hesaplarda değil, takımın GitHub Organization'nında tutar.**
 **README, Wiki ve kurulum dokümanlarını güncel tutar.**
 **Açıklayıcı commit mesajları ve kapatılmış issuelar vardır.**
 **Yarışma sonrası sürümleri tag ile işaretlenebilir.**

### 6) Otonom araç projesindeki yeri
 Birçok birimin paralel çalışabilmesi için her birim kendi modülü veya paketi üzerinde branch'lerinde çalışır.
 Modüller arasındaki arayüzler önceden belirlenir.
 main her zaman araçta çalıştırılabilecek kodu tutar.
 Simülasyonda test edilmemiş kodun main'e girmesi branch protection ve Actions ile engellenir.
 Her testten önce araca yüklenen commit tag ile işaretlenir.
 Test notlarına tag ya da commit hash'ı yazılır.
 Test başarısız olursa bir önceki çalışan tag'e hemen dönülebilir.

### 7) Dikkat edilmesi gerekenler
 **Şifre, API anahtarı gibi gizli bilgilerin repoya yüklenmesi**
 **Büyük dosyaların repoya eklenmesi**
 **Derleme çıktıların commit'lenmesi**
 **Doğrudan main'e push yapıp çalışan kodu bozmak**
 **git push --force ile başkalarının commit'lerini silmek**
 **Günlerce commit atmamak ve tek dev bir commit yapmak**
 **Çalışmaya başlamadan pull yapmamak**
 **Commit atıp push etmeyi unutmak**
