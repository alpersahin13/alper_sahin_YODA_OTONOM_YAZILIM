## 1. Git ve GitHub Temel Kavramları

Bu bölümdeki örneklerin hepsini kendi bilgisayarımda denedim. Önce `git-deneme` adında küçük bir test reposu açtım, içine `notlar.txt` diye tek bir dosya koydum ve commit, branch, merge, push, pull işlemlerini bu dosya üzerinden yaptım. Aşağıdaki terminal çıktıları o denemelerden alındı.

### 1.0 Hazırlık: Git'e kendimi tanıtmak

Git her commit'e onu kimin yaptığını yazar. Bu yüzden ilk iş olarak adımı ve e-posta adresimi tanıttım:

```bash
git config --global user.name "Alper Şahin"
git config --global user.email "alperahin01@gmail.com"
git config --global --list
```

```text
user.name=Alper Şahin
user.email=alperahin01@gmail.com
```

İlk denememde komutun başındaki `git` kelimesini unuttum ve `bash: --global: command not found` hatası aldım. Küçük bir hata ama terminalde her harfin önemli olduğunu gösterdi.

### 1.1 Repository (Depo)

Repository, bir projenin bütün dosyalarını ve bu dosyaların **tüm geçmişini** tutan klasördür. Normal bir klasörden farkı, içinde gizli bir `.git` klasörü olmasıdır. Git kimin, ne zaman, neyi değiştirdiğini bu klasörde saklar.

Repository iki yerde olabilir:
- **Local (yerel) repo:** Kendi bilgisayarımdaki kopya.
- **Remote (uzak) repo:** GitHub gibi bir sunucudaki kopya. Takım bu kopya üzerinden ortak çalışır.

**Örnek:** Boş bir klasörü repository'ye çevirdim.

```bash
mkdir git-deneme
cd git-deneme
git init
```

```text
Initialized empty Git repository in C:/Users/Alper/git-deneme/.git/
```

Bu komuttan sonra terminaldeki satırın sonunda `(master)` yazmaya başladı. Bu, artık bir repo içinde olduğumu ve `master` branch'inde durduğumu gösteriyor.

### 1.2 Stage (Hazırlık Alanı)

Stage, bir dosyayı değiştirmekle o değişikliği kaydetmek arasındaki **bekleme alanıdır**. Git, değiştirdiğim her şeyi otomatik olarak kaydetmez. Hangi değişikliklerin bir sonraki commit'e gireceğini `git add` ile ben seçerim. Bunu bir kargo kutusuna benzetiyorum: önce göndereceğim eşyaları kutuya koyuyorum (stage), sonra kutuyu kapatıp gönderiyorum (commit).

**Örnek:** Bir dosya oluşturup `git add` öncesinde ve sonrasında `git status` çıktısına baktım.

```bash
echo "Merhaba" > notlar.txt
git status
```

```text
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        notlar.txt
```

Dosya kırmızı renkte, "Untracked" yani **takip edilmeyen** olarak görünüyor.

```bash
git add notlar.txt
git status
```

```text
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   notlar.txt
```

Dosya artık yeşil ve "Changes to be committed" altında. Stage'e alınmış, commit'lenmeye hazır.

Daha sonra dosyayı tekrar değiştirdiğimde `git status` farklı bir şey gösterdi:

```text
Changes not staged for commit:
        modified:   notlar.txt
```

Dosya artık takip edildiği için "untracked" yerine "modified" (değiştirildi ama henüz stage'e alınmadı) yazıyor.

> `git add` sırasında `LF will be replaced by CRLF` diye bir uyarı aldım. Bu bir hata değil. Windows ve Linux satır sonlarını farklı karakterlerle yazıyor, Git de bunu otomatik düzelteceğini haber veriyor.

### 1.3 Commit

Commit, stage'deki değişikliklerin **kalıcı bir kaydıdır**, yani projenin o anki halinin fotoğrafı gibi. Her commit'in benzersiz bir kimliği (hash), bir yazarı, bir tarihi ve ne yapıldığını anlatan bir mesajı vardır. Gerektiğinde herhangi bir commit'e geri dönülebilir.

**Örnek:**

```bash
git commit -m "İlk notu ekle"
```

```text
[master (root-commit) 61be2e0] İlk notu ekle
 1 file changed, 1 insertion(+)
 create mode 100644 notlar.txt
```

- `61be2e0` → commit'in kısa kimliği (hash).
- `root-commit` → bu, repodaki ilk commit.

```bash
git log
```

```text
commit 61be2e078e0ef94220a75d295f01f44e468e1b22 (HEAD -> master)
Author: Alper Şahin <alperahin01@gmail.com>
Date:   Sun Nov 8 22:53:12 2026 +0300

    İlk notu ekle
```

`git config` ile girdiğim ad ve e-postanın commit'e yazıldığını burada görebiliyorum. `HEAD -> master`, şu anda bu commit'in üzerinde durduğumu gösteriyor.

### 1.4 Branch (Dal)

Branch, projenin **ayrı bir çalışma kolu**dur. Ana koda (`main` ya da `master`) dokunmadan yeni bir özellik denemek veya bir hatayı düzeltmek için yeni bir branch açılır. Branch'te yapılan değişiklikler, birleştirilene kadar ana branch'i etkilemez.

**Örnek:** `yeni-ozellik` adında bir branch açıp orada dosyaya bir satır ekledim.

```bash
git switch -c yeni-ozellik
echo "Branchten gelen satir" >> notlar.txt
git add notlar.txt
git commit -m "Branchte yeni satir ekle"
```

```text
Switched to a new branch 'yeni-ozellik'
[yeni-ozellik 393cc22] Branchte yeni satir ekle
 1 file changed, 1 insertion(+)
```

Sonra `master`'a geri dönüp dosyaya baktım:

```bash
git switch master
cat notlar.txt
```

```text
Merhaba
```

Branch'te eklediğim satır `master`'da **yok**. Branch'lerin birbirinden bağımsız olduğunu en net burada gördüm.

> Not: `>` dosyanın üzerine yazar, `>>` ise dosyanın sonuna ekler.

### 1.5 Merge (Birleştirme)

Merge, bir branch'teki değişiklikleri başka bir branch'e **aktarma** işlemidir. Genelde bir özellik kendi branch'inde tamamlanıp test edildikten sonra `main`'e merge edilir.

**Örnek:** `yeni-ozellik` branch'ini `master`'a birleştirdim.

```bash
git merge yeni-ozellik
cat notlar.txt
```

```text
Updating 61be2e0..393cc22
Fast-forward
 notlar.txt | 1 +
 1 file changed, 1 insertion(+)

Merhaba
Branchten gelen satir
```

```bash
git log --oneline --graph
```

```text
* 393cc22 (HEAD -> master, yeni-ozellik) Branchte yeni satir ekle
* 61be2e0 İlk notu ekle
```

Çıktıdaki **Fast-forward**, ben branch'te çalışırken `master`'a yeni bir commit eklenmediği anlamına geliyor. Git bu durumda ayrı bir birleştirme commit'i oluşturmuyor, `master`'ın işaretçisini ileri taşıyor. İki branch'e de ayrı ayrı commit atılmış olsaydı Git bir **merge commit** oluşturacaktı. İki branch aynı satırı farklı şekilde değiştirmiş olsaydı da **merge conflict** çıkacaktı (bkz. 2.3).

### 1.6 Push (Gönderme)

Push, yerel repodaki commit'leri **uzak repoya (GitHub'a) gönderme** işlemidir. Push yapılmayan commit'ler sadece benim bilgisayarımda kalır ve takım arkadaşlarım onları göremez.

**Örnek:** GitHub'da boş bir `git-deneme` reposu oluşturdum, sonra yerel repomu ona bağlayıp gönderdim.

```bash
git branch -M main
git remote add origin https://github.com/alpersahin13/git-deneme.git
git push -u origin main
```

```text
info: please complete authentication in your browser...
Writing objects: 100% (6/6), 481 bytes | 120.00 KiB/s, done.
To https://github.com/alpersahin13/git-deneme.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

- `git branch -M main` → `master` branch'inin adını, GitHub'da yaygın olarak kullanılan `main` olarak değiştirdi.
- `git remote add origin ...` → GitHub'daki reponun adresini `origin` adıyla kaydetti.
- `-u` → yerel `main`'in GitHub'daki `main`'i takip etmesini sağladı. Bundan sonra sadece `git push` yazmam yetti.
- İlk push'ta Git, tarayıcıdan GitHub'a giriş yapmamı istedi. Sonraki push'larda tekrar sormadı.

### 1.7 Pull (Çekme)

Pull, push'un tersidir: uzak repodaki **yeni commit'leri yerel repoya indirip birleştirir**. Takımda başka biri kod gönderdiyse, çalışmaya başlamadan önce `git pull` yapmak gerekir.

**Örnek:** Başka birinin değişiklik yapmasını taklit etmek için GitHub'ın web sitesinde `notlar.txt` dosyasını düzenleyip commit'ledim, sonra bilgisayarıma çektim.

```bash
git pull
```

```text
From https://github.com/alpersahin13/git-deneme
   393cc22..32f85c7  main       -> origin/main
Updating 393cc22..32f85c7
Fast-forward
 notlar.txt | 2 ++
 1 file changed, 2 insertions(+)
```

GitHub'da düzenleme yaparken metni yazmayı unutup sadece iki boş satır eklemişim. Commit'in adı da bu yüzden "Add empty lines to notlar.txt" oldu. Yine de pull'un nasıl çalıştığını gösterdi. Ardından eksik satırı bilgisayarımdan ekleyip tüm döngüyü (değiştir → add → commit → push) bir kez daha yaptım:

```text
[main 9afcb87] Bilgisayardan yeni satir ekle
To https://github.com/alpersahin13/git-deneme.git
   32f85c7..9afcb87  main -> main
```

### 1.8 Ek: Clone

Bu ödevin reposunu GitHub'da README ile oluşturdum ve `git clone` ile bilgisayarıma indirdim. Clone, uzak bir repoyu bütün geçmişiyle birlikte kopyalar ve `origin` bağlantısını kendisi kurar.

```bash
git clone https://github.com/alpersahin13/alper_sahin_YODA_OTONOM_YAZILIM.git
```

Sonra ödevin istediği gibi `odev_2` branch'ini açtım ve bu dokümanı onun içine ekledim:

```bash
git switch -c odev_2
mkdir odev_2
git add odev_2
git commit -m "odev_2 klasoru ve dokuman dosyasini ekle"
git push -u origin odev_2
```

Burada şunu öğrendim: **Git boş klasörleri takip etmez.** Klasörün GitHub'a gidebilmesi için içinde en az bir dosya olması gerekir.

### 1.9 Özet: Kullandığım Komutlar

| Komut | Ne işe yarar |
|---|---|
| `git init` | Klasörü bir repository'ye çevirir |
| `git status` | Hangi dosyaların değiştiğini veya stage'de olduğunu gösterir |
| `git add <dosya>` | Değişikliği stage'e alır |
| `git commit -m "mesaj"` | Stage'dekileri kalıcı olarak kaydeder |
| `git log --oneline --graph` | Commit geçmişini gösterir |
| `git switch -c <ad>` | Yeni branch açar ve o branch'e geçer |
| `git switch <ad>` | Var olan bir branch'e geçer |
| `git merge <ad>` | Başka bir branch'i bulunduğum branch'e birleştirir |
| `git remote add origin <url>` | Uzak repo adresini kaydeder |
| `git push` | Commit'leri GitHub'a gönderir |
| `git pull` | GitHub'daki yeni commit'leri indirir |
| `git clone <url>` | Uzak repoyu bilgisayara kopyalar |

## 2. Takımlar Neden Git ve GitHub Kullanır?

### 2.1 Versiyon kontrolüne neden ihtiyaç duyulur?

Versiyon kontrolü olmayan bir projede kod genelde şu şekilde paylaşılır: USB bellek, WhatsApp'tan zip dosyası ya da ortak bir Drive klasörü. Bu durumda karşılaşılabilecek sorunlar şunlardır:

- **Hangi dosyanın güncel olduğu bilinmez:** `kontrol.py`, `kontrol_yeni.py`, `kontrol_son.py`, `kontrol_son_GERCEKTEN_son.py`...
- **Birbirinin işini ezme:** İki kişi aynı dosyayı düzenleyip paylaşınca, son gönderen öncekinin değişikliklerini farkında olmadan siler.
- **Neyin, neden değiştiği bilinmez:** Araç dün düzgün çalışıyordu, bugün çalışmıyor. Ama aradaki değişikliği kimin yaptığını ve neyi değiştirdiğini kimse bilmiyor.
- **Geri dönülemez:** Hatalı bir değişiklikten sonra çalışan sürüm kaybolmuş olabilir. Yarışmadan bir gün önce yaşanırsa bu ciddi bir sorun olur.

**Commit geçmişi bu sorunları şöyle çözer:** Her commit kimin, ne zaman, neyi ve hangi mesajla değiştirdiğini kaydeder. `git log` ile geçmiş, `git diff` ile iki sürüm arasındaki fark satır satır görülebilir.

**Hatalı bir değişiklikten sonra çalışan sürüme dönmek için birkaç yol vardır:**

```bash
git log --oneline                 # hatalı commit'i bul
git revert 9afcb87                # o commit'i geri alan YENİ bir commit oluşturur (geçmiş silinmez)
git switch --detach 393cc22       # eski bir sürümü sadece denemek için geçici olarak aç
git restore notlar.txt            # henüz commit'lenmemiş değişiklikleri çöpe at
```

Ortak çalışılan branch'lerde `git revert` tercih edilmelidir. Geçmişi silmediği için diğer takım üyelerinin reposunu bozmaz. `git reset --hard` da geri dönmeyi sağlar ama geçmişi değiştirdiği için dikkatli kullanılmalıdır.

### 2.2 Git ile GitHub arasındaki fark

| | **Git** | **GitHub** |
|---|---|---|
| Ne? | Versiyon kontrol **aracı** (yazılım) | Git repolarını barındıran **web platformu** (servis) |
| Nerede çalışır? | Kendi bilgisayarımda, internetsiz de çalışır | İnternette, github.com üzerinde |
| Kim yaptı? | Linus Torvalds, 2005 (Linux çekirdeği için) | GitHub Inc., 2008 (2018'den beri Microsoft'un) |
| Ne sağlar? | commit, branch, merge, geçmiş takibi | Uzak repo, pull request, code review, Issues, Actions, Wiki... |

Kısacası Git işin **motoru**, GitHub ise bu motoru takım olarak kullanmayı kolaylaştıran **ortak garaj**. Git, GitHub olmadan da kullanılabilir. GitHub ise Git olmadan bir işe yaramaz.

**GitHub'a alternatif platformlar:**

| Platform | Öne çıkan özelliği |
|---|---|
| **GitLab** | Dahili CI/CD sistemi güçlü, kendi sunucuna kurulabiliyor (self-hosted) |
| **Bitbucket** | Atlassian ürünü, Jira ile entegrasyonu çok iyi |
| **Azure DevOps (Azure Repos)** | Microsoft'un kurumsal çözümü, iş takibi ve pipeline'larla birlikte geliyor |
| **Gitea / Forgejo** | Hafif, açık kaynak, küçük bir sunucuya hatta Raspberry Pi'ye bile kurulabiliyor |
| **Codeberg** | Kâr amacı gütmeyen, Forgejo tabanlı ücretsiz platform |

### 2.3 Ekip çalışmasına katkıları

Birden fazla kişinin birbirinin işini bozmadan çalışabilmesinin temeli **branch**'lerdir. Her üye kendi işi için ayrı bir branch açar (`lidar-filtre`, `serit-takibi` gibi), `main` branch'i ise her zaman çalışan kodu tutar.

**Pull Request (PR):** Bir branch'teki işi `main`'e birleştirmek için yapılan **resmi istek**tir. PR'da hangi dosyaların ve satırların değiştiği görünür, kod birleştirilmeden önce takım tarafından incelenir.

**Code Review:** Başka bir takım üyesinin PR'daki kodu okuyup yorum yapması, hata veya iyileştirme önermesi ve onay vermesidir. Böylece hatalar `main`'e girmeden yakalanır. Ayrıca herkes başkalarının yazdığı kodu da öğrenmiş olur.

**Merge Conflict:** İki branch **aynı dosyanın aynı satırını** farklı şekilde değiştirdiğinde Git hangisinin doğru olduğuna karar veremez ve bu kararı insana bırakır.

**Örnek senaryo:** Ahmet ve ben aynı ayar dosyasında çalışıyoruz.

1. `main`'deki `ayarlar.yaml` dosyasında `max_hiz: 20` yazıyor.
2. Ben `hiz-ayari` branch'inde bunu `max_hiz: 25` yapıyorum.
3. Ahmet `guvenlik` branch'inde aynı satırı `max_hiz: 15` yapıyor ve onun PR'ı önce merge ediliyor.
4. Ben kendi PR'ımı merge etmeye çalışınca Git şunu gösteriyor:

```text
<<<<<<< HEAD
max_hiz: 15
=======
max_hiz: 25
>>>>>>> hiz-ayari
```

5. Ahmet'le konuşup doğru değere birlikte karar veriyoruz (mesela okul bahçesindeki testler için 15). İşaretleri silip dosyayı düzeltiyoruz, ardından `git add` ve `git commit` ile conflict'i çözüyoruz.

Conflict aslında Git'in bir korumasıdır: Ahmet'in değişikliği sessizce silinmek yerine karar verilmek üzere önümüze getirilir.

### 2.4 GitHub'ın proje yönetimi özellikleri

| Özellik | Ne işe yarar | Takımda nasıl kullanılabilir |
|---|---|---|
| **Issues** | Görev, hata ve fikir kaydı. Etiket, sorumlu kişi ve hedef tarih (milestone) atanabilir | "Kamera kalibrasyonu yapılmalı", "Durak tabelası algılanmıyor" gibi işler issue olarak açılır ve bir üyeye atanır |
| **Projects** | Issue'ları Kanban panosunda gösterir (Yapılacak / Yapılıyor / Bitti) | Haftalık toplantılarda kimin ne üzerinde çalıştığı panodan takip edilir |
| **README ve Markdown** | Reponun ana sayfasındaki tanıtım ve kurulum dokümanı | Projenin ne olduğu, nasıl derlenip çalıştırılacağı yazılır |
| **Wiki** | Repoya bağlı çok sayfalı dokümantasyon | Donanım bağlantı şemaları, sensör ayarları, yarışma kuralları notları tutulur |
| **Actions** | Push veya PR geldiğinde otomatik çalışan işler (CI/CD) | Her PR'da kodun derlenip derlenmediği ve testlerin geçip geçmediği otomatik kontrol edilir |
| **Releases ve Tags** | Belirli bir commit'i sürüm olarak işaretler | "v1.0 – Saha testi 1" gibi sürümler oluşturulur |
| **Branch protection** | `main`'e doğrudan push'u engeller, PR ve onay zorunlu tutulur | Kimsenin test edilmemiş kodu yanlışlıkla `main`'e göndermemesi sağlanır |
| **Discussions** | Forum tarzı soru-cevap alanı | Yeni üyelerin soruları ve teknik tartışmalar burada kalıcı olarak tutulur |

### 2.5 Kulüp ve takımlar için önemi

Öğrenci takımlarında her yıl birileri mezun olur ve yerine yeni üyeler gelir. Kod sadece kişisel bilgisayarlarda durursa, o kişi ayrılınca kod da, o koda harcanan emek de kaybolur. Bunu önlemek için yapılabilecekler:

- **Kodu kişisel hesaplarda değil, takıma ait bir GitHub Organization'da tutmak.** Böylece kimse ayrılınca repo onunla birlikte gitmez.
- **Organization'da birden fazla yönetici olması.** Tek kişi mezun olduğunda erişim kaybolmaz.
- **README, Wiki ve kurulum dokümanlarını güncel tutmak.**
- **Açıklayıcı commit mesajları ve kapatılmış issue'lar.** Bunlar "bu kod neden böyle yazıldı?" sorusunun cevabını yıllar sonra bile verir.
- **Yarışma sonrası sürümleri tag ile işaretlemek.** Örneğin "2026 yarışmasında kullanılan kod" her zaman bulunabilir olur.

**Yeni üyeler için faydası:** Yeni gelen biri repoyu clone'lar, README'yi okuyup projeyi kendi bilgisayarında çalıştırır, commit geçmişinden ve eski PR'lardan projenin nasıl geliştiğini öğrenir. Başlangıç için de "good first issue" etiketli küçük görevleri alabilir. Bu sayede her yıl sıfırdan başlamak yerine önceki yılların birikiminin üzerine inşa edilir.

### 2.6 Otonom araç projesindeki yeri

Otonom araç yazılımı birçok alt sistemden oluşur: **algılama** (kamera, LiDAR), **konumlama ve haritalama**, **yol planlama**, **araç kontrolü** (direksiyon, gaz, fren), **simülasyon** ve **gömülü sistemler**. Bu birimlerin paralel çalışabilmesi için:

- Her birim kendi modülü veya paketi üzerinde (ör. ROS 2 paketleri) kendi branch'lerinde çalışır.
- Modüller arasındaki arayüzler (hangi topic'e hangi mesaj tipiyle veri gönderildiği) önceden belirlenir ve dokümante edilir. Böylece algılama birimi kendi kodunu değiştirirken planlama biriminin kodu bozulmaz.
- `main` her zaman araçta çalıştırılabilecek kodu tutar. Yeni özellikler PR ve code review ile eklenir.
- Simülasyonda test edilmemiş kodun `main`'e girmesi branch protection ve Actions ile engellenir.

**Saha testinde kullanılan sürümün takibi:** Sahada "hangi kod yüklüydü?" sorusunun cevabı her zaman net olmalıdır. Bunun için:

```bash
git tag -a saha-testi-1 -m "1. saha testi - serit takibi denemesi"
git push origin saha-testi-1
```

- Her testten önce araca yüklenen commit **tag** ile işaretlenir.
- Test notlarına bu tag ya da commit hash'i yazılır. Böylece "3. testteki hata hangi koddaydı?" sorusu kesin olarak cevaplanabilir.
- Test başarısız olursa bir önceki çalışan tag'e hemen dönülebilir.

**Önceki ödevde incelediğim KTR'lerdeki durum:** Ödev 1'de üç takımın KTR'sini inceledim: ANKA (Hazır Araç, 2022), İTÜ Racing Driverless (Özgün Araç) ve VOLANS (Hazır Araç). Karşılaştırma tablomda "Ortak çalışma ve kurulum" diye bir satır açmıştım. Üç raporda da Git, GitHub veya Docker kullanımından **hiç bahsedilmiyordu**. Takımlar iş bölümünü anlatmıştı: ANKA aylık iş planı ve kişi bazlı iş paketleri hazırlamıştı, İTÜ Racing Driverless ise görüntü işleme, ROS, direksiyon-fren gibi alt ekiplere ayrılmıştı. Ama bu ekiplerin kodu nasıl birleştirdiği ve sürümleri nasıl takip ettiği yazılmamıştı. VOLANS'ın raporunda algoritmaların araçta tam test edilemediği ve teknik sorunlar yaşandığı yazıyordu. ANKA'nın CAN yazılımını takıma tanınan 5 günlük araç süresinde test etmesi de sahada geçirilen zamanın ne kadar kısıtlı olduğunu gösteriyor. Bu kadar kısa test sürelerinde "araçta hangi kod çalışıyordu?" ve "son çalışan sürüme nasıl döneriz?" sorularının hızlıca cevaplanabilmesi gerekiyor. Bence KTR'lerde sürüm kontrolü ve test edilen sürümlerin takibi ayrı bir başlık olarak anlatılmalı. Bizim takımın raporunda da bunu göstermek fark yaratabilir.

### 2.7 Dikkat edilmesi gerekenler

| Sorun | Nasıl önlenir |
|---|---|
| Şifre, API anahtarı gibi gizli bilgilerin repoya yüklenmesi (public repoda herkes görür) | `.gitignore` kullanmak, gizli bilgileri ayrı ve commit'lenmeyen bir dosyada tutmak. Yanlışlıkla yüklendiyse anahtarı hemen değiştirmek, çünkü silmek geçmişten kaldırmaz |
| Büyük dosyaların (rosbag kayıtları, eğitilmiş modeller, videolar) repoya eklenmesi | `.gitignore` ile dışarıda bırakmak ya da Git LFS kullanmak |
| `build/`, `install/`, `log/` gibi derleme çıktılarının commit'lenmesi | `git add .` yerine ne eklendiğine bakmak, bu klasörleri `.gitignore`'a yazmak |
| Doğrudan `main`'e push yapıp çalışan kodu bozmak | Branch'lerde çalışmak, `main` için branch protection açmak |
| `git push --force` ile başkalarının commit'lerini silmek | Ortak branch'lerde force push yapmamak |
| "düzeltme", "asdf", "son" gibi anlamsız commit mesajları | Ne yapıldığını anlatan kısa ve net mesajlar yazmak |
| Günlerce commit atmamak ve tek dev bir commit yapmak | Küçük ve anlamlı adımlarla sık commit atmak |
| Çalışmaya başlamadan pull yapmamak (gereksiz conflict'ler çıkar) | Her çalışma öncesi `git pull` yapmak |
| Commit atıp push etmeyi unutmak (bilgisayar bozulursa iş kaybolur) | Gün sonunda mutlaka push etmek |
